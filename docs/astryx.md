# How ui-common is built on Astryx

This page explains the architecture of `@lablup/ui-common` from 0.2 on. The
rules that follow from it are in [CONTRIBUTING.md](../CONTRIBUTING.md).

## The picture

```
product ──> @lablup/ui-common ──> @astryxdesign/core          (dependency, exact pin)
                  │           ──> @astryxdesign/theme-neutral (dependency, exact pin)
                  │           ──> @astryxdesign/cli           (dependency, exact pin)
                  │           ··> @astryxdesign/lab           (optional peer, exact pin)
                  └─────────────> @stylexjs/stylex            (peer, ^0.19)
```

A product depends on ui-common and nothing from `@astryxdesign/*`. ui-common
owns the Astryx version. Core is a dependency, not a peer, so each product does
not have to pin it again, and pnpm patches on core still apply graph-wide.

## Three kinds of exports

### 1. The Astryx mirror

Every subpath in `@astryxdesign/core`'s `exports` map exists in ui-common under
the same name. `@astryxdesign/lab` lands under `lab`, and
`@astryxdesign/theme-neutral` under `theme/neutral`.

| Astryx                                   | ui-common                               |
| ---------------------------------------- | --------------------------------------- |
| `@astryxdesign/core/Button`              | `@lablup/ui-common/Button`              |
| `@astryxdesign/core/Table/utils`         | `@lablup/ui-common/Table/utils`         |
| `@astryxdesign/core/theme/tokens.stylex` | `@lablup/ui-common/theme/tokens.stylex` |
| `@astryxdesign/core/astryx.css`          | `@lablup/ui-common/astryx.css`          |
| `@astryxdesign/core/locales/ko-KR.json`  | `@lablup/ui-common/locales/ko-KR.json`  |
| `@astryxdesign/lab`                      | `@lablup/ui-common/lab`                 |
| `@astryxdesign/theme-neutral/built`      | `@lablup/ui-common/theme/neutral/built` |

Each mirror is one line:

- A script subpath is `export * from "@astryxdesign/core/Button"`. The build
  keeps it that way, because every `@astryxdesign/*` import is external. Astryx
  is never bundled into ui-common. A bundled copy would carry its own React
  contexts (`Theme`, i18n, `SizeContext`), and components would stop seeing
  the consumer's providers.
- A stylesheet subpath is `@import "@astryxdesign/core/astryx.css"`. The
  consumer's bundler resolves that `@import` from ui-common's install
  location, so it works under pnpm's strict layout, where the app itself cannot
  see `@astryxdesign/core`.
- The locale catalogs are JSON, which cannot re-export. They are copied from
  the installed core at build time, so they always match the pinned version.

The mirror is generated by `scripts/gen-exports.mjs` from the installed
packages. Nobody curates it. `exports.exclude.json` is the only way to hide a
subpath, and each entry says why and what replaces it.

The root barrel (`@lablup/ui-common`) is generated too. It lists core's root
exports by name, minus the names of excluded subpaths, then ui-common's own
customs. Listing names explicitly, instead of `export *`, makes a name clash
visible in review.

A test regenerates everything in memory and compares it with the committed
files. An Astryx bump therefore fails CI until someone reruns the generator and
reads the diff. That diff is the upgrade review.

### 2. The Lablup theme

`@lablup/ui-common/theme/lablup` is an Astryx theme source. It extends neutral
and changes only the brand: the orange accent seed, the four status hues, and
the font family name. Info has no Astryx token, so the theme declares
`--uic-color-info` as a theme-local token.

`astryx theme build` compiles it into `theme/lablup/built` (a JS theme object
marked as pre-built) and `theme/lablup/theme.css`. Both are committed.
`pnpm run theme:check` fails when they are stale.

Product palettes stay in the products, as their own `defineTheme` over
`lablupTheme` or `neutralTheme`.

### 3. ui-common's own

- **Custom components**, listed in `exports.customs.json`. They are built on
  Astryx primitives and tokens and never share a name with Astryx. Each is in
  the root barrel and at `@lablup/ui-common/components/<Name>`; `Modal` also
  has a top-level subpath, `@lablup/ui-common/Modal`, because it stands where
  the hidden `@lablup/ui-common/Dialog` would. The excluded subpath's own
  names that `Modal` re-exports unchanged (`DialogHeader` and the Dialog
  types) are the one sanctioned overlap with Astryx: they are Astryx's.
- **`ui-common.css`**, the global sheet. It holds rules with no component to
  hang on, today only the scrollbar.
- **`i18n-catalog`** and **`ui-common-locales/*.json`**, ui-common's strings.
- **`legacy-tokens.css`**, a deprecated bridge from the 0.1 tokens. Removed in
  0.3.

## Cascade layers

```css
@layer reset, theme, base, astryx-base, astryx-theme, ui-common, components, utilities;
```

The consumer declares this once, first. Astryx puts its component styles in
`astryx-base`, and themes put overrides in `astryx-theme`. ui-common's styles
go in `ui-common`, after both, so a ui-common component that wraps an Astryx
primitive can restyle it. The app's `components` layer comes after ui-common,
so the app always has the last word.

## StyleX

Astryx ships precompiled. Its `dist` has no `stylex.create` left, only
class-name maps and runtime `stylex.props` calls, and all rules are in
`astryx.css`. So a consumer needs no StyleX compiler. It only needs the
`@stylexjs/stylex` runtime, which is why it is a peer.

A consumer that writes its own StyleX imports tokens from
`@lablup/ui-common/theme/tokens.stylex`. The StyleX compiler recognises a theme
import by the `.stylex` suffix on the import specifier, and emits
`var(--color-accent)` and the like for every Astryx token, because their keys
start with `--`.
Import the tokens from the root barrel and the compiler rejects the build.

ui-common's own components use plain CSS. If ui-common ever compiles StyleX
itself, it uses `classNamePrefix: "uic"` and `--`-prefixed `defineVars` keys.

## Strings

ui-common has no i18n context of its own. Its components call an internal
`useUicTranslator()`, which reads Astryx's `InternationalizationProvider`:

1. the provider's `overrides` for the locale, then each parent locale
2. the provider's `messages` for the locale, then each parent locale
3. the English `defaultMessage` in ui-common's catalog

Astryx's own translator falls back to Astryx's English catalog, which has no
`uic.*` keys. That is why ui-common needs step 3.

A consumer supplies ui-common's translations once, at the provider, together
with Astryx's own: `mergeMessages({ "ko-KR": astryxKo }, uiCommonMessages)`.

## The Astryx CLI

`astryx.integration.mjs` registers ui-common with the Astryx CLI. A project
that depends on ui-common loads it implicitly. It contributes the
`astryx docs ui-common` topic, component docs for ui-common's own components
(`astryx component Modal`), and four lines for the managed agent block,
including "Use Modal, not Dialog".

The CLI pairs each `{Name}.doc.mjs` with a same-stem `{Name}.tsx`, and the
manifest has no way to point at source elsewhere. ui-common ships no source,
so each doc sits beside a one-line `.tsx` that re-exports the component.
`doctor integration validate` accepts that; `astryx swizzle` on one copies
the re-export, not an implementation.

The CLI cannot hide a core component, so the hiding happens one level up, in
ui-common's own bin.

## The ui-common CLI

`bin/ui-common.mjs` wraps the pinned `@astryxdesign/cli`. It resolves that CLI
from ui-common's own install location, so a consumer needs no Astryx
dependency.

- **Passthrough.** Any Astryx command runs the pinned bin; its output is
  rewritten from `@astryxdesign/*` to `@lablup/ui-common/*` and from `astryx …`
  to `ui-common …`, and a name `exports.exclude.json` hides gets a note naming
  its replacement. Astryx's lookups find core by walking up from the working
  directory, which a pnpm consumer of ui-common does not have; for read-only
  commands the bin then runs Astryx in a throwaway directory of symlinks to the
  project's packages plus the Astryx packages ui-common pins.
- **`agents`.** Astryx renders its agent block in memory; ui-common rewrites
  it, adds its own rules, and keeps it between UI-COMMON markers, which
  `astryx init` and `astryx upgrade` leave alone.
- **`upgrade`.** Codemod steps keyed by ui-common version, on jscodeshift and
  postcss (the engines the Astryx CLI uses). See
  [CONTRIBUTING.md](../CONTRIBUTING.md#the-upgrade-tool).
- **`sync-astryx`.** The maintainer's pin bump. See
  [CONTRIBUTING.md](../CONTRIBUTING.md#bumping-astryx).

`agents` and the upstream codemods use Astryx CLI internals
(`foundation/agent-docs`, `assets/codemods/registry.mjs`) that are not its
public API. The pin is exact, and `test/cli/` exercises both, so a bump that
moves them fails the tests.

## Checks

| Command                                  | What it guards                                                                                                 |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `src/exports.test.ts`                    | generated surface matches the installed Astryx                                                                 |
| `pnpm run theme:check`                   | built Lablup theme matches its source                                                                          |
| `src/globalStyles.test.ts`               | legacy tokens cover all 122 names; layers; real tokens                                                         |
| `src/components/componentStyles.test.ts` | every component sheet: one `@layer ui-common`, `uic-` classes, Astryx tokens, no colour literal, no focus rule |
| `src/migrationMap.test.ts`               | `migration/0.1-to-0.2.json` matches what was removed, what replaces it, and the renamed classes                |
| `pnpm run check:pack`                    | every export target is packed; every bare import is a dependency or peer; every Astryx locale is mirrored      |
| `pnpm run check:integration`             | the CLI accepts the manifest, and the tarball carries it                                                       |
| `test/upgrade/`                          | the upgrade codemods turn each fixture project into its expected output, and a second run changes nothing      |
| `test/cli/`                              | output rewriting, the agent block, the registry, upstream codemods, and `sync-astryx`'s guards                 |
| CI `external-install`                    | the tarball installs, type-checks and builds in a clean project, with Astryx's sheets in the bundle            |
